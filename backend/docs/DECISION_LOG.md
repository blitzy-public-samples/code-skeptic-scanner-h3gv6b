# Decision Log

This log is the single source of truth for *why* the Code Skeptic Scanner backend is built the way it
is. Each entry records one decision that a competent engineer could reasonably have made
differently, together with the alternatives that were available, the reasoning that selected this
option and the risks the option carries.

Code in this repository never carries rationale. A comment states provenance facts — the source file
and line range it was ported from, or that the construct is net-new — and points here with
`see docs/DECISION_LOG.md`, optionally naming the entry that governs it. Reasoning, alternatives and
risks live in this file only.

**Identifier allocation.** `DL-001` … `DL-060` are the identifiers of the decision inventory
committed in the Agent Action Plan §0.7.2; an artifact citing one of those identifiers refers to that
inventory. Identifiers from `DL-061` onward are allocated by this log for decisions the committed
inventory does not cover.

| DL-061 | `entity/Setting.java` maps the two `settings` columns whose names are reserved SQL words with JPA-standard quoted identifiers — `@Column(name = "\"key\"")` and `@Column(name = "\"value\"")` — keeping the physical names exactly as `backend/app/db/models.py:L42-43` declared them. `settings.description`, the table name `settings` and every `ai_tools` column stay unquoted. | (a) Plain `@Column(name = "key")` / `@Column(name = "value")`. (b) Rename the columns, e.g. `setting_key` / `setting_value`. (c) Set `hibernate.globally_quoted_identifiers=true` for the whole application. (d) Rely on `hibernate.auto_quote_keyword=true` being set in the active profile. (e) Append `NON_KEYWORDS=KEY,VALUE` to the H2 JDBC URL. (f) Backtick quoting, ``@Column(name = "`key`")``. | `KEY` is reserved in H2 2.x and in MySQL, and `VALUE` is reserved in the SQL standard and in H2, so (a) fails outright: H2 2.3.232 rejects `create table settings_unquoted (key varchar(255), value varchar(255))` with `Syntax error … expected "identifier"` — measured, not assumed. (b) breaks the column-name parity mandate (AAP G2 / TR-3) and would falsify the traceability matrix. (c) changes identifier case-sensitivity for all four tables and twenty columns to solve a two-column problem. (d) is a global switch present in `application-test.yml` but not in the specified main profile, so the mapping has to stand on its own in production; the JPA-standard form works with or without it. (e) is vendor-specific, fixes only H2, and would have to be threaded through a `DATABASE_URL` that IR4 keeps opaque and vendor-neutral. (f) is MySQL-flavoured, whereas Hibernate renders the JPA-standard form with each dialect's own quote character — measured as `"key"` on H2 and PostgreSQL and `` `key` `` on MySQL — so one mapping covers all three supported vendors. | Quoted identifiers are case-sensitive: on H2 the columns exist as lower-case `key` and `value` while unquoted identifiers are folded to upper case (measured: the created `settings` table has columns `DESCRIPTION`, `key`, `value`). Hand-written native SQL must therefore quote them — `select "key", "value" from settings` — and schema-metadata assertions must expect the lower-case names. Nothing inside the application is affected, because Hibernate emits the quoted form consistently in DDL and DML (measured: `insert into settings (description,"value","key") values (?,?,?)`). The `not null` that appears on the primary key in the generated DDL is JPA's own `@Id` semantics, not an added constraint. |
| DL-062 | `service/SentimentAnalysisService.calculateDoubtRating` returns `10.0` for a `Double.NaN` score through an explicit guard placed ahead of the transcribed expression; the transcribed lines themselves stay byte-for-byte `(1 - sentimentScore) * 5` followed by `Math.max(0.0d, Math.min(10.0d, doubtRating))`. | (a) Keep `Math.max`/`Math.min` alone, letting NaN propagate. (b) Replace the clamp with ordered conditional expressions that reproduce Python's comparison fall-through across the whole domain. (c) Reject a NaN score with an exception. (d) Substitute a neutral `5.0`. | Parity is measured against the source expression `max(0, min(10, doubt_rating))` at `backend/app/services/sentiment_analysis.py:L32`. Python's built-ins return their first argument when a comparison is false, so `min(10, nan)` is `10` and `max(0, 10)` is `10`: the source yields `10` for a NaN score, confirmed by executing the expression. Java's `Math.min`/`Math.max` instead propagate NaN, so (a) returns NaN from a method contracted to return `0.0`–`10.0` and lets a non-finite value reach `tweets.doubt_rating`. NaN is the *only* input where the two differ — ±0.0 and ±∞ agree — so one guard restores bit-identical behaviour over the full `double` domain (verified against a python3 reference for 18 inputs). (b) is equally correct but discards the two transcribed lines the specification fixes verbatim (min nested inside max, no `Math.clamp`, no reordering), which makes the port harder to diff against its source. (c) and (d) invent behaviour the source does not have. | The bound `10.0` now appears twice in the method — as the upper bound and in the guard — and both must move together if the scale ever changes. A NaN score is mapped to the maximum doubt rating rather than reported as an anomaly; the score returned by the Natural Language API is logged at `INFO` by `analyzeSentiment`, so the input stays observable. |
| DL-063 | `config/DatabaseUrlTranslator.TranslatedDatabaseUrl.toString()` renders all three components — `jdbcUrl`, `username` and `password` — as the single fixed marker `***REDACTED***`, returning the same text for every instance. | (a) The compiler-generated record `toString()`. (b) Redact only the password, printing the URL and username in clear. (c) Emit a sanitised URL with the user-info component and credential-bearing query properties stripped. (d) Render the markers tri-state, distinguishing an absent value (`null`) and an empty value (`""`) from a present one. (e) Drop the override and forbid logging the record by convention. | A value that arrives already in JDBC form is passed through exactly as supplied (DL-064) and may embed credentials in its user-info component or in query properties such as `?user=…&password=…`, so any rendering of the URL text can disclose a credential (CWE-532); (a) and (b) both do, and (b) additionally printed the username, which is credential material. (c) would require a second security-critical parser and would still reveal host and database name for no diagnostic gain. (d) still discloses whether a credential is configured at all, which is the same disclosure that was removed from `config/ScannerProperties` for its fourteen redacted components; using one marker keeps a single convention across both types and cannot leak by construction. (e) depends on every present and future caller remembering, and the record is the natural thing to interpolate into a startup log or an assertion failure. | Someone diagnosing a connection failure cannot read the URL out of a log record that interpolates this record, and cannot tell from that record whether a credential was configured. The values remain available through the `jdbcUrl()`, `username()` and `password()` accessors for code that genuinely needs them, and `translate` still logs the resolved vendor at `INFO` on the translation path. |
| DL-064 | `config/DatabaseUrlTranslator.translate` tests the value exactly as supplied for the literal lower-case prefix `jdbc:` using `String.startsWith`, and returns that same value unchanged. No value is trimmed, case-folded or otherwise normalised anywhere in the class, including on the parse path. | (a) Trim first and match the prefix case-insensitively, returning the trimmed value. (b) Trim for detection only but return the original value. (c) Keep trimming and document it as intended behaviour. | The specified contract is that a JDBC value is returned unchanged and is "not parsed, normalised or stripped" (AAP §0.6.5.1 / IR4), which a trimmed or case-expanded return value does not satisfy — and the class Javadoc already claimed that behaviour while the code trimmed, so the two disagreed. (b) would hand a whitespace-padded URL to the DataSource it had just recognised, converting a clear startup failure into a driver-level one. (c) makes silent correction part of the contract and keeps the class free to alter a value the specification says it must not touch. Consuming the value exactly as supplied also matches SQLAlchemy, which rejects a padded URL rather than trimming it, so failing fast is the source behaviour as well. | A `DATABASE_URL` padded with whitespace, or written with an upper-case `JDBC:` prefix, now fails at startup instead of being silently corrected: padded input raises `DATABASE_URL is not a parseable URL (Illegal character in scheme name)` and an upper-case prefix raises the unsupported-scheme error naming the supported schemes. Both fail fast at boot with an actionable message and neither can produce a half-configured DataSource, but an operator who previously relied on the trim will see a new startup failure. |
| DL-065 | `exception/BadRequestException`, `exception/NotFoundException` and `exception/ResponseGenerationException` each declare `private static final long serialVersionUID = 1L;` and each is `final`. | (a) Carry `@SuppressWarnings("serial")` and declare no identifier. (b) Leave the `javac -Xlint:all` `[serial]` warning in place. (c) Avoid `RuntimeException` so the types are not serializable. | No instance of these types crosses a serialization boundary — each is created, thrown, caught by the error-handling advice in the same JVM and rendered as a JSON body — so any of (a) and a declared identifier are equally sound on the merits, and the tree must be clean under `-Xlint:all`, which rules out (b). A declared identifier was chosen because it is the resolution the review named first, because it removes the warning at its cause rather than hiding the category, and because these three types now expose a closed set of client-visible messages through static factories (DL-066): a fixed identifier makes the wire-literal contract explicit rather than leaving it to a compiler-generated value that changes whenever the class shape does. (c) is not available — an unchecked exception has to extend `RuntimeException`, which is `Serializable`. | The literal `1L` is a value no consumer checks today, so it carries no information; if one of these types is ever genuinely serialised across versions the identifier must be maintained deliberately. Nothing in the service serialises an exception, and introducing that would be an architectural change carrying its own entry. |
| DL-066 | `exception/BadRequestException` and `exception/NotFoundException` declare a private constructor and expose their approved wire literals only through public constants and one static factory per literal (`tweetIdRequired()`, `updateDataRequired()`, `noValueProvided()`, `tweetNotFound()`, `responseNotFound()`, `responseNotFoundOrUpdateFailed()`, `settingNotFound()`); `exception/ResponseGenerationException` carries one fixed message and exposes only `()` and `(Throwable)`. A triggering throwable attaches through `withCause(Throwable)` or the cause constructor and is reachable only through `getCause()`. | (a) Keep a public `String` constructor, as the literal reading of AAP §0.4.1.7 implies, and rely on call sites passing only the approved literals. (b) Validate a supplied message against an allow-list at construction time. (c) Map arbitrary messages to a generic body inside the error-handling advice. | A public `String` constructor lets any caller — including one relaying a database driver message, a vendor API response or a value read from configuration — put arbitrary server-side text into the `error` value of a client response (CWE-209). (a) makes that a convention rather than a guarantee. (b) adds a runtime check for something the type system can make unrepresentable. (c) moves the guarantee into a component that does not exist yet and would still let the wrong text reach a log-and-rethrow path. Closing the constructor makes the eight wire literals the complete client-visible message set by construction, and each factory carries its literal unaltered so every one still round-trips through `getMessage()` character for character, which is what AAP §0.4.1.7 and IR1 actually require. | `new NotFoundException("…")` and `new BadRequestException("…")` no longer compile; call sites must use the factories. No source in the module constructs these types today, so nothing needed changing, but a later checkpoint adding controllers or services must use the factory names. Adding a new client-visible 4xx literal now requires editing the exception type as well as its call site. |
| DL-067 | `dto/LoginRequest` overrides `toString()` to render **both** components as `***REDACTED***` and binds its `password` member write-only (`@JsonProperty(access = WRITE_ONLY)`); `dto/TokenResponse` overrides `toString()` to render `accessToken` as `***REDACTED***` while rendering `tokenType` and `expiresIn` as they are. Deserialization and serialization are otherwise untouched: `LoginRequest` still binds both JSON members and `TokenResponse` still emits `access_token`, `token_type` and `expires_in`. | (a) Rely on a documented "instances of this type are never logged" invariant, which is what the records originally carried. (b) Redact the credential component only, leaving the submitted principal name in clear. (c) Redact without the write-only binding. (d) Omit the credential component from the record and pass it separately. | A record's compiler-generated `toString()` renders every component, so a plain interpolation into a log line, an assertion message or an exception message discloses a submitted password or a live bearer token (CWE-532); (a) makes that a convention that every present and future caller has to remember, which is the fragility the review flagged.
