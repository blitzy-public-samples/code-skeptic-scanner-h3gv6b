# Decision Log

This log is the single source of truth for *why* the Code Skeptic Scanner backend is built the way it
is. Each entry records one decision that a competent engineer could reasonably have made
differently, together with the alternatives that were available, the reasoning that selected this
option and the risks the option carries.

Code in this repository never carries rationale. A comment states provenance facts — the source file
and line range it was ported from, or that the construct is net-new — and points here with
`see docs/DECISION_LOG.md`, optionally naming the entry that governs it. Reasoning, alternatives and
risks live in this file only.

**Completeness invariant.** Every `DL-` identifier cited by any artifact in this repository has a
row in the table below carrying all four of its content columns — decision, alternatives, rationale
and risks. A citation is never satisfied by an entry that lives somewhere else.

**Revision.** When a decision changes, its entry is rewritten in place under the same identifier so
that a citation always resolves to the behaviour the code has now; the earlier form survives in
version history only — see DL-099.

**Identifier allocation.** `DL-001` … `DL-060` are the identifiers of the decision inventory
committed in the Agent Action Plan §0.7.2, and each one whose decision is embodied by a delivered
artifact is populated below. Identifiers from `DL-061` onward are allocated by this log, in ascending
order and never reused, for decisions the committed inventory does not cover — the inventory was
written before the tree existed and therefore could not name a decision that only the delivered code
raises. The current range is `DL-001` … `DL-219`.

**Ownership.** One entry owns one subject, and one subject is owned by exactly one entry. A citation
names the entry that owns the subject the reader is looking at, never an entry that merely mentions
it: an entry about the comment convention does not authorise a mapper, and an entry about choosing a
client library does not cover that client's lifecycle. When an entry is found to carry more than one
subject, it is split and each successor takes one subject — `DL-077` was split this way into
`DL-200`, `DL-201` and `DL-202`. When two entries are found to describe one subject, the cited one is
kept and the other becomes a pointer to it.

**Superseded entries.** An entry that no longer describes the delivered tree is rewritten in place —
never deleted and never renumbered — either as a correction or as a pointer opening
`**Superseded by DL-xxx.**` that names the entry which now owns its subject. This keeps every
identifier cited from any commit resolvable. The entries rewritten this way are listed in DL-099.

## Identifier reconciliation against the Agent Action Plan

The Agent Action Plan commits a sixty-entry decision inventory in §0.7.2 and allocates `DL-001` …
`DL-060` to it. This log holds more identifiers than that, and this section states exactly how the
two relate so that the difference reads as a documented allocation rather than as drift.

**`DL-001` … `DL-060` — the committed inventory.** Each identifier in this range means what §0.7.2
says it means. Where a decision in that inventory is embodied by a delivered artifact, its row below
carries the full four columns; the identifier is never reused for a different decision.

**`DL-061` onward — implementation-phase allocations.** These cover decisions the committed inventory
does not enumerate, because they arise from the delivered code rather than from the plan: a provider
API's actual behaviour, a framework mechanism, a defect found while validating, or a limitation that
had to be accepted with reasons. They are allocated sequentially by this log and are cited only from
code, tests and this file — never from the Agent Action Plan, which is frozen. Their existence does
not amend the plan; where one of them records a departure from a plan directive, the departure is
stated in that row's own Rationale column, which is what Rule 1 requires of a deviation.

**Revision rather than supersession.** When a decision changes, its row is rewritten in place under
the same identifier so a citation always resolves to the behaviour the code has now, and the
withdrawn form is preserved as a named alternative in that row so the change is legible. The rows
rewritten in this way are `DL-034`, `DL-041`, `DL-059`, `DL-080`, `DL-082`, `DL-083`, `DL-084`,
`DL-088`, `DL-090`, `DL-096`, `DL-123`, `DL-153`, `DL-177`, `DL-178`, `DL-183`, `DL-185` (discharged
by `DL-189`), `DL-187`, `DL-190`, `DL-195` and `DL-216`. `DL-139` is the one row this round turned
into a pointer instead, because `DL-080` already owned its subject.

**Consistency between rows.** Two rows must never describe the same construct differently. `DL-083`
owns the adapter's `IllegalStateException` codes and the service-boundary conversion to
`ResponseGenerationException`; `DL-178` defers to that contract and owns the decision to fail rather
than return empty text, plus the check order.

**What the no-rationale rule governs.** The prohibition is on *comments*: a comment states provenance
facts and points here. It does not govern program output. One runtime diagnostic —
`config/DatabaseUrlTranslator`'s warning for the `mariadb` scheme — explains in its own text why the
bundled driver cannot serve a MariaDB server and what to do instead, because a warning an operator
cannot act on is not a warning (`DL-187`, and the actionability requirement of AAP IR8). That text is
emitted to the log, not written in a comment, and it is the only place in the tree where reasoning
appears outside this file.

**Where the authoritative statement lives.** For a build coordinate, `backend/pom.xml` is
authoritative and this log explains it; a comment in that file that contradicts the file's own
declarations is a defect, which is what `DL-204` records and closes. For behaviour, the code is
authoritative and this log explains it. For scope, the Agent Action Plan is authoritative and neither
the code nor this log may widen it.

**Population state.** All sixty committed identifiers `DL-001` … `DL-060` are populated, and the
log-allocated range runs unbroken from `DL-061` to `DL-219`. Every identifier in `DL-001` … `DL-219`
therefore names a row here — two hundred and nineteen rows with no gap and no repeat — so a citation
of any of them resolves and no identifier is reserved without content. The bidirectional mapping between source constructs and delivered artifacts is
`docs/TRACEABILITY_MATRIX.md`; it names the entry that governs every net-new target, and every
identifier it names is a row here.
